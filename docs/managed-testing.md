# Managed OPEN testing (Pi candidate)

The Pi OPEN pipeline uses the same central worker configuration for test owner, implementer and reviewer. The production selection is `openai-codex/gpt-6-sol` at reasoning `high`; source admission does not pin that identity for mock inference or other operator-configured Pi workers. Bounded tasks and legacy non-Pi executions keep their existing paths; an explicitly managed-testing ticket on a non-Pi harness is refused. This source change does not activate or change the operator's worker configuration.

Each Pi OPEN ticket's `## Testing plan` must declare `Broad regression: none`, or `Broad regression: required` followed immediately by `Command: <operator-approved command>`. The approved testing-workflow-v1 phase ticket uses its original `npm test` clause. Commands are ticket-owned, never supplied through the test tools; a broad run is admitted once per review round, after the reviewer records a READY/no-repair assessment and the current selected tests pass. Incomplete attempts consume the round's allowance.

The project supplies a **committed, clean** `.architect/test-runner.json` at OPEN admission. This exact repository-relative file is project-owned source: onboard or update it in a separately authorized project change and land that commit **before** starting a fresh OPEN feature admission. Managed source commits and landings include it without force-add; all other `.architect/` and `.zvec-grep/` paths remain operational/excluded (pre-staged operational paths are refused). OPEN admission never bootstraps an uncommitted runner file.

Schema 1 remains `{ "schema":1, "command":"node", "args":[], "directory":"tests", "extension":".mjs" }` and executes `node <selected-file>`. Schema 2 is the fixed TypeScript profile `{ "schema":2, "profile":"node-tsx-test", "directory":"tests", "extension":".test.ts" }` and executes `node --import tsx --test <selected-file>` (the consumer project must provide `tsx`). No additional config keys, agent-supplied commands/flags/argv or shell are accepted. Directory and extension are constrained, and selected files must exist beneath the directory and bound worktree after realpath resolution. Traversal, absolute paths, symlink escapes and broad `run.mjs`/`run.test.ts` entrypoints are refused. The broad ticket-owned checkpoint remains separate from per-file focused runs; `npm test` is never a focused target.

Admission checks the regular config file against the committed execution-base blob and rejects missing, staged, dirty or invalid profiles **before** issuing worker authority. Its byte digest and base commit are kept in managed state; selection, runs, reviews and checkpoints carry the admitted digest. Runner changes after admission invalidate current evidence and cannot be legalized by rerunning under the modified profile. A new approved execution base is needed for a changed config. This does not authorize onboarding iso-notation's project config/policy, activating a source release, or resuming its feature ticket; those remain separate project-owned steps.

The record under the workflow state directory (`managed-tests/<execution id>.json`) stores selection, per-target launches and elapsed outcomes, tested working-state digests, categorized review assessments, and checkpoint attempts. The execution result references and includes this record. A PASS requires matching current reviewer focused evidence and, when required, checkpoint evidence. A changed file/selection or runner authority cannot inherit a previous PASS. READY, material FAIL, DECISION_NEEDED, INCOMPLETE and nonblocking suggestions are distinct; an unexplained initial test failure is not automatically expected-red. No retry-to-green, caching, sandbox, shell-wide detection or performance guarantee is implied.
