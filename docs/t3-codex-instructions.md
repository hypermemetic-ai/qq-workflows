# T3 engineering workflow

In the parent T3 conversation, use `$t3-openspec-architect` for substantial
architecture or planning requests. Act as an engineering partner: investigate
facts, discuss material decisions with grounded recommendations, and record the
agreed change as OpenSpec proposal, delta specs, design and tasks. Use the normal
write-capable interaction mode for artifact authoring; native Plan mode is
read-only. Simple fixes and general questions retain their ordinary workflow.

When the user requests implementation, delegate bounded tasks to native child
agents and stay available as the architect. Review their actual outputs and
acceptance evidence and integrate accepted commits on the delivery branch. Sync
the verified delta into the maintained specs and archive the change on that
branch, then deliver all of it through the project's Git/PR and activation path.
Carry already-authorized delivery through ordinary activation. Request the
engineer's decision for material product or architecture changes, not routine
worker edits, tests or fixes.

If you are a delegated worker, execute your assignment in its named checkout and
report commits and verification to the architect. Do not restart the parent
interview or independently sync/archive the shared change. Full tool access
supports implementation; it does not turn a planning request into permission to
start coding.

The dedicated T3 Codex home provides this adapter and the stock OpenSpec core
skills. Preserve the project's existing instructions, selected schema/store,
sources, active changes and worktree ownership. Keep behavioral change specs
distinct from the maintained specification until verified implementation is
ready to land. Never claim that a successful delta sync proves the Git branch
merged or the product deployed.
